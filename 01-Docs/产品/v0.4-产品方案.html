产品方案 · v0.4 评审修订稿

知树 KnowTree

一个长期、简约的个人知识储备软件 —— 把总结「丢」进去，它自动归类、挂上知识树、去重合并、建立互链、生成卡片，并在你需要时把旧知识送回眼前。
只做核心闭环，不加法。

移动端 App 个人云端 · 多端同步 AI 归类 · 去重 · 互链 P0 范围已冻结
一句话定位：「知识随手丢，树自会长大。」你负责记录，它负责把零散知识整理成结构清晰、彼此互联的个人知识树，并用卡片与回溯让你真的把知识留下来。

00评审结论：这轮改了什么

方向我认同，「零分类记录 + 自动结构化」是真实痛点，值得做。但 v0.3 是一份好的概念稿，还不是一份能直接开发、能验收的方案：范围偏满、规则缺失、没有量化标准。以下五条是主要判断，本轮已据此改写全文。

定位成立，但用户还太宽

高

「个人知识储备」无法指导取舍：学生、工程师、内容创作者、收藏党要的东西完全不同。已补首发人群、高频场景、明确不服务的人，以及和现有做法的差异。

最大风险是「纠错成本」，不是 AI 不够强

高

自动归类一旦出错，用户要花比手动分类更多的时间去改。v0.3 只写了「没有就自动新建节点」，没有防节点泛滥的门槛，也没有误合并的恢复路径。这是会直接杀死产品的点，已补规则与兜底。

冷启动没解

高

新用户是一棵空树，前 20 条恰恰是体验最差的时候：无可匹配节点、互链稀疏、推荐无内容。已补导入引导、可选骨架、推荐降级策略。

「绝对不加法」和清单自相矛盾

中

六项核心 + 四项可玩，实际接近 10 项，MVP 会失焦。已按 P0 / P1 重排，把吉祥物、深度推荐、图片卡片移出关键路径。

没有可验收的标准

中

「自动」「秒级」「更准」都无法测试，研发和测试只能各自发明标准。已补关键规则、条目状态、指标定义和 M1 验收清单。

◈ 本轮改动范围

· 新增：目标用户与差异、价值假设与验证方案、关键规则表、条目状态与失败兜底、指标与验收、风险与对策。

· 修正：数据模型字段错位（tags / entry_tags 混行），补状态、哈希、软删除、任务队列、版本表与 RLS。

· 调整：范围分 P0/P1；底部 Tab 由 4 个收敛为 3 个；深度推荐降级为 P1 并给规则兜底。

· 保留：产品定位、技术栈选型、视觉方向、v0.3 已确认的决策全部不变。

01定位与目标用户

先把「给谁、在什么时刻用、替代了什么」说清楚，后面的功能取舍才有依据。

🎯

首发人群

每周至少产出 3 篇学习/研究总结，且资料已经散落在 2 个以上工具里的人：研究生、工程师、转行学习者。

⏱

高频场景

学完一个知识点 → 写总结 → 丢进 App → 一周后被回溯卡片送回眼前 → 需要时检索复用。

🚫

暂不服务

团队共享知识库、内容创作者发布、纯收藏不复盘的人。这些需求会把产品推向协作与编辑器，直接背离闭环。

它替代了什么

现有做法能解决缺口
手动分类笔记（文件夹 / 标签）记录稳定、可检索每次记录都要先决定「放哪」；长期分类会失控；不自动去重、不建立关系
稍后读 / 剪藏工具收集快只收不用；没有结构；内容越多越不敢打开
通用 AI 对话即时答疑对话不沉淀为可检索资产，下次还得重新问
文件夹 + 全文搜索找得到依赖记得关键词；知识之间没有关系

◈ 差异化就三条，其余都是支撑

· 把分类从用户身上移走 —— 记录时零决策，归类是系统的事，且用户随时能改、系统会记住。

· 把结构化变成自动结果 —— 去重、互链、挂树不是用户维护出来的，是收录时自动产生的。

· 用回溯保证二次使用 —— 不做「收藏即学会」的假闭环，旧知识必须被重新送回眼前。

02价值假设与验证

这个产品赌的是三件事。M0 不是为了「跑通链路」，而是为了验证这三条假设是否成立；任何一条不成立，方案要改，而不是硬做。

假设为什么关键M0 怎么验达标线（建议）不达标怎么办
H1 用户愿意「不分类直接丢」 这是整个产品的前提。若用户仍要先想分类，产品就没有存在理由 Web 原型 + 10 位目标用户，7 天真实使用 人均收录 ≥15 条；≥60% 的条目未手动改分类 退化为「半自动」：AI 给 3 个候选节点，用户一键选，仍不要求手写分类
H2 自动归类与去重足够可信 一次误合并就可能让用户不敢再丢东西进来 200 条真实总结离线盲测，人工标注对照 归类 Top1 命中 ≥70%（含可接受的父节点）；误合并率 ≤2%；100% 可撤销 收紧自动挂载阈值，低置信全部进「待确认」；去重只提示不合并
H3 回溯能带来二次使用 没有二次使用，产品就只是个更聪明的收藏夹 4 周内测，统计回溯卡片打开与反馈 打开率 ≥35%；「记得/忘了」反馈率 ≥20% 改推送时机与卡片形态（图文/一问一答），不改核心链路

M0 的产出不是「能点」，是「有数」

M0 必须产出三份东西：准确率报告（归类/去重/互链各多少）、阈值表（写回本文档第 04 节）、10 人使用记录（收录量、纠偏率、放弃原因）。没有这三份，不进 M1。

03首发范围 · P0 / P1

「不加法」的正确含义不是功能少，而是关键路径上只有一件事：让「丢 → 结构化 → 被送回」跑顺。以下按是否影响这条路径分层。

能力优先级首发做到什么程度后置 / 不做
文本 / Markdown / PDF / Word 收录P0粘贴、导入、批量丢；一丢即收，无需填字段网页剪藏、邮件导入、微信转发（P1 后）
AI 归类收编P0自动标题/摘要/标签/候选节点，低置信进「待确认」，支持拖拽纠偏长文改写、自动扩写、多语言互译

知识树 + 卡片P0树可视化 + 节点生长；卡片用模板（标题/摘要/标签）AI 插画卡片（P1，异步补）

离线草稿P0断网可写，联网自动同步，不重复入库离线阅读全库（P1）
图片收录 / OCRP1先做 OCR 转文字；图片作为卡片后置拍照即卡片、手写识别（不做）

卡片收藏夹P1首发作为「知识库」的筛选视图，不单独做 Tab收藏册/集邮式展示（P1）
吉祥物养成P1首发只保留静态形象与成长值，不做装扮系统表情/装扮解锁（P1，美术成本高）

◈ 明确「不做」什么（首发排除）

社交与分享广场、多人协作与共享空间、复杂富文本编辑器、插件/开放 API、多父节点归类、自动摘要长文、独立 Web 正式版。

判断标准只有一句：它是否让「丢 → 结构化 → 被送回」更快发生。不能，就不做。

冷启动兜底：前 20 条怎么不难用

① 首次进入给「从现有笔记导入」入口，支持粘贴多段或批量文件，让树在第一天就有内容。

② 提供可选主题骨架（如「机器人 / 算法 / 论文」），可一键采用，也可从零开始；不强制。

③ 条目不足 10 条时隐藏互链与推荐模块，只展示树与卡片，避免满屏「暂无内容」。

④ 条目不足 3 条时不推送回溯卡片，改为收录引导（对应第 06 节第 7 步的兜底）。

04关键规则：能开发，也能测试

这一节是 v0.3 最大的缺口。每个环节都写清触发条件、判定规则、失败时怎么办、用户能否恢复；标「建议」的数值待 M0 校准。

环节规则失败 / 异常用户可恢复动作
收录 文本 ≤5 万字直接收；超长截断展示并保留原文件。同一文件哈希 / 同一 URL 命中已有条目时提示「已收录过」，默认不新增。 超大文件、加密 PDF、扫描件无文本层 保留原文件可下载；可手动粘贴正文
解析 PDF/Word/Markdown 后端解析抽正文；图片走 OCR（P1）。解析结果与原文件一起入库。 解析失败重试 3 次（退避），仍失败标「解析失败」并保留原文件 手动重试、手动补正文、删除重传
AI 归类 输出标题、一句话摘要、标签、候选节点 Top3 + 置信度。置信 ≥0.75 且节点存在 → 自动挂载；0.50–0.75 → 挂载但标「待确认」；<0.50 → 进「未分类」收件箱，不自动新建节点。 模型超时 / 限流 / 返回结构不合法 条目仍入「未分类」，后台重试；用户可手动挂树
新建节点 同一父节点下已有 ≥3 条同主题内容且无匹配节点时，才「建议新建」；新建需用户确认（支持批量）；层级 ≤3 级；单用户节点数 >200 时提示合并。 AI 反复建议碎节点 一键合并节点、批量重挂、节点改名
去重合并 第一道：内容哈希完全相同 → 直接提示重复。第二道：同节点内向量相似度 ≥0.90 → 强提示合并；0.80–0.90 → 弱提示「可能相关」。默认只提示，不自动合并；合并为软合并，原文与互链保留。 误判（两篇不同但相似）；合并后想找回 一键拆分，恢复原文、标签、互链；30 天内可撤销
知识互链 每条自动建 1–3 条最高分链接，分数 <0.70 不建；同节点内不建链（树已表达层级）；单条自动链上限 5 条，超出需手动添加。 链太多变成噪音；撤销后被反复重建 单条撤销并记录负反馈，同类链接不再自动重建
卡片 入树即生成卡片（标题 / 摘要 / 标签 / 来源）。首版用模板与纯色纹理，不依赖文生图，保证 8 秒内可见。 摘要为空、标题过长 手动编辑标题/摘要；重新生成摘要
检索 关键词走全文索引，语义走向量；结果按 相关度 × 新鲜度 排序；覆盖标题、摘要、正文、标签（OCR 文本在 P1 接入后纳入）。 空结果、中文分词差、OCR 噪声 自动降级为语义检索；展示「相关节点」而非空页
回溯 每日 1–3 张；权重 = 久未查看天数 × 重要度（收藏、被链次数）；排除 7 天内已看；「记得/忘了」调整下次间隔。 推送打扰、旧知识过多 可关推送、可调时间；连续忽略自动降频
同步与冲突 条目级后写覆盖，保留最近 10 个历史版本；节点重命名冲突以最新为准并提示。 离线草稿重复上传；两设备同时编辑 查看历史版本、一键回滚
删除与导出 删除进回收站 30 天；注销需二次确认 + 7 天冷静期，到期彻底删除数据与文件。导出 MD（含 front-matter）与 JSON（全表）。 导出缺字段、附件丢失 导出前校验条目数与附件数，不一致则阻断并提示

05条目状态与失败兜底

一条知识从「丢进来」到「被删掉」会经过 7 个状态。状态不写清，就会出现「转圈很久不知道成没成」和「失败后内容丢了」这两类致命体验。

状态进入条件用户看到什么可执行动作
草稿本地输入，未上传列表顶部「待同步」标识编辑、删除、立即同步
解析中已上传，正文抽取中卡片骨架 + 进度，不阻塞继续收录取消、查看原文件
待确认归类置信 0.5–0.75，或命中疑似重复「待确认」角标 + 建议节点/重复项确认、改节点、合并、保留为独立条目
已入树归类完成并挂载卡片 + 所属节点 + 互链改节点/标签、编辑、收藏、删除
已合并用户确认合并主条目下显示「已合并 N 条」，可展开拆分、查看原文
回收站删除回收站列表，30 天倒计时恢复、彻底删除
已删除超期或彻底删除不可见无（注销时一并清除）

失败兜底的三条硬规则

① 任何失败都不能丢原文 —— 解析失败、AI 失败都保留原文件与原始文本，用户可手动补。

② 失败不阻塞下一次收录 —— 失败任务进队列后台重试，前端不弹阻塞式弹窗。

③ 失败必须可解释 —— 提示「文件已加密，无法读取正文」这类具体原因，不用「处理失败，请重试」。

06一次收录的完整旅程

主路径全自动，但每一步都有兜底。用户只需要做两个决定：要不要合并、分类对不对。

1

丢入内容

粘贴文本，或导入文档/图片，支持批量。不填任何字段，不做任何选择。

失败时：超大或加密文件提示具体原因，原文件可下载。

2

解析与提取

后端解析 PDF / Word / Markdown 正文；图片走 OCR（P1）。原文件与正文一起入库。

失败时：自动重试 3 次，仍失败标「解析失败」，可手动补正文。

3

AI 理解与去重检测

生成标题、摘要、标签；哈希 + 向量双通道检测重复，给出「合并 / 保留」建议。

失败时：进「未分类」收件箱，后台重试，不阻塞后续流程。

4

自动归类挂树

高置信直接挂载；中置信挂载并标「待确认」；低置信留在收件箱，不自动新建节点。

失败时：用户拖拽纠偏，系统记录偏好，下次同类内容优先该节点。

5

建立知识互链

基于语义与标签，自动关联 1–3 条最相关的既有知识，也可手动连线。

失败时：可单条撤销，撤销后同类链接不再自动重建。

6

入索引与节点生长

写入全文索引与向量索引；对应节点「生长」一截，卡片即时可见。

失败时：索引失败仍可浏览，标注「暂不可搜索」，后台补建。

7

在需要时被送回

每日回溯 1–3 张旧卡片；检索时按相关度 + 新鲜度返回；P1 起补充深度推荐。

失败时：无足够旧内容时不推送空卡片，改为提示「再收录 3 条即可开启回溯」。

07核心数据模型

v0.3 的 tags / entry_tags 挤在同一行、字段缺失，直接照着建表会漏关系。以下为修订版：补状态、哈希、软删除、任务队列、版本表，并统一 RLS 隔离。

建表时必须一起定下的四件事

① 全表启用 RLS：user_id = auth.uid()，个人数据不靠应用层过滤。

② 软删除统一用 deleted_at，所有查询默认过滤，回收站才有 30 天可恢复。

③ embeddings 用 pgvector，记录 model 与 dim，换模型时可增量重建而不污染旧数据。

④ content_hash 是去重第一道，入库前计算，比向量检索便宜且确定。

  • React Navigation — 底部 3 个 Tab（知识树 / 知识库 / 我的）。
  • 自研简约主题 — 暗色底、单点缀色、圆角卡片，克制不花哨。
后端 · Supabase
  • Postgres + pgvector — 条目、节点、边、向量一套库解决。
  • Auth — 邮箱登录，多端同步与 RLS 的基础。
  • Express + Vercel Functions — 同源 API、解析与 AI 编排、定时任务补偿。
AI · OpenAI 兼容接口
  • LLM（豆包 / DeepSeek / Kimi） — 标题、摘要、标签、候选节点。
  • Embedding — 检索、去重、互链共用同一套向量。
  • 文生图（Seedream） — 仅 P1 卡片插画，异步补齐。
成本与限制
  • 每条知识 ≈ 1 次 LLM + 1 次 embedding；插画另计且异步。
  • 降级策略 — 高峰期用轻量模型做归类，摘要失败不阻塞入树。
  • 预算上限 — 内测期按人设月额度，超出排队而非静默失败。
  • 待核算 — 单条成本需按实际调用价实测，M0 给出数。

09可玩性：只留两项进关键路径

可玩性不是坏东西，但它不能挡住闭环。四项里只有两项直接服务主循环，其余放 P1。

◈

知识树生长

P0 · 成就可视化

每次收录，对应节点生长一截。让「积累」这件事被看见，是最低成本的长期动力。

↻

每日回溯卡片

P0 · 对抗遗忘

每天 1–3 张旧卡片，按「久未看 + 重要度」加权。它是 H3 假设的验证载体，必须首发。

♡

卡片收藏夹

P1 · 集邮式沉淀

首发作为知识库筛选视图存在；独立收藏册与集邮展示等留存数据证明有效再做。

◆

吉祥物养成

P1 · 长期陪伴

首发只保留形象与成长值。表情、装扮需要持续美术投入，不进关键路径。

克制原则

不抽卡、不充值、不强制社交、不做复杂数值。可玩性只服务「记录 → 成长 → 回顾」，一旦需要额外解释才懂，就是做过头了。

10指标与验收

没有指标，「更准」「更快」就无法判断。以下阈值为建议初值，M0 实测后校准；但指标定义从第一版就该固定，否则每次都在换尺子。

◈ 北极星指标

周有效沉淀数 = 本周收录、且 30 天内被再次打开（回溯或检索点击）的条目数。

选它的理由：只统计「收录」会奖励囤积，只统计「打开」会奖励刷旧内容。两者相乘才代表知识真的沉淀下来了。

维度指标建议达标线怎么用
激活首日收录条目数≥3 条低于此值说明「丢」的门槛还太高
首周收录条目数≥10 条低于此值不进留存分析，先修引导
留存次周留存≥40%核心健康度
4 周留存≥25%决定是否值得继续投入 M2
归类Top1 命中率≥70%含「可接受的父节点」也算命中，按人工抽检
人工纠偏率≤25%高于此值说明自动归类在制造负担
去重误合并率≤2%红线指标，超标立即收紧阈值
重复提示采纳率≥50%过低说明提示太吵或不准
互链自动链撤销率≤15%过高说明链接是噪音，宁少不多

检索空结果率 / 首条点击率≤10% / ≥60%空结果率高说明索引或分词有问题

M1 验收清单（可直接当测试用例）

  • 断网收录：断网写入 3 条 → 恢复网络后全部入库，且与云端已有内容不产生重复条目。
  • 重复导入：同一份 PDF 二次导入 → 提示「已收录过」，默认不新增，可强制新增。
  • 低置信不新建：新主题内容首次收录 → 进入「未分类」收件箱，不自动创建节点。
  • 误合并可恢复：合并两条后拆分 → 原文、标签、互链全部恢复，主条目不受影响。
  • 失败不丢内容：上传加密 PDF → 提示具体原因，原文件可下载，条目保留在列表。
  • 撤销后不重建：撤销一条自动互链 → 同一对条目不再自动建链。
  • 回溯不空转：知识库不足 3 条时 → 不推送空卡片，改为引导收录。
  • 导出完整：导出 100 条 → MD 与 JSON 条目数一致，附件链接可访问。
  • 注销彻底：注销冷静期结束 → 各表记录、Storage 文件、向量全部清除，账号无法登录。
  • 隔离有效：用 A 账号 token 请求 B 账号条目 → 返回空，不泄露任何字段。

12实施路线

先验证假设，再写 App。每个阶段都有退出标准，达不到就停在原地修，不靠延期掩盖。时间为建议，需按实际投入确认。

M0

假设验证 · 2 周（建议）

Web 原型 + 200 条真实总结离线跑归类/去重/互链；10 位目标用户真实使用 7 天。此阶段不写正式 App。

退出标准：H1/H2 达标，产出准确率报告、阈值表、使用记录。不达标 → 调整方案，不进 M1。

M1

MVP · 6–8 周（建议）

Expo + Supabase：P0 全部能力、知识树与模板卡片、检索、回溯、导出与删除、离线草稿。P1 一律不进本次发布。

退出标准：验收清单 10 项全过；内测 4 周留存 ≥25%；误合并率 ≤2%。

M2

打磨与扩展 · 按留存数据决定

P1 能力：OCR 与图片卡片、深度推荐、收藏册、吉祥物装扮、端到端加密；以及准确率、动效与性能打磨。

进入条件：4 周留存 ≥25% 且周有效沉淀数仍在增长。否则先修留存，不扩功能。

15待定项与建议默认值

这三项需要你拍板。我先给建议，避免方案停在「等你回答」上；你改，我按你的改。

① 图片的收录方式？

建议：先做 OCR 转文字（P1 早期），图片本身作为卡片放 P1 后期。

理由：卡片已有模板承担视觉，图片存储、裁切、清晰度与成本都不轻；而 OCR 直接服务「检索得到」，对闭环更有价值。

② 是否已有 AI 平台云资源 / 账号？

建议：M0 使用可配置的 OpenAI 兼容接口；未配置密钥时按规则降级，站点仍可完整运行。

理由：M0 要的是准确率数据，不是最优模型；先跑起来，再按实测成本决定正式接入哪家。

③ 命名「知树 KnowTree」是否保留？

建议：保留为工作名，M1 前再做商店名与商标查重。

理由：名字不影响验证，但现在改会牵连图标、文案与截图，等闭环成立再定更省。

④ 新增：M0 是否接受「先不写 App」？

建议：接受。M0 用 Web 原型验证 H1/H2，2 周内拿到数，再决定 M1 怎么做。

理由：归类与去重的效果只有真实数据能回答；先写 App 等于把最大的不确定性推到最贵的阶段。
